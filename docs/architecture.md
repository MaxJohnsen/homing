# Architecture

How Homing is built. The behavior it must have is in the [specification](spec.md). This document can change without changing the concept.

## Shape

Homing is a modular monolith: one deployment with a transactional database, derived indexes, background workers and optional model inference. External agents stay independent and use Homing through MCP.

| Component | Responsibility |
|---|---|
| MCP server | The interface agents use |
| Web app | The interface people use |
| Core | Spaces, guidance, context, permissions, publishing checks, proposals |
| Runner | System routines: capture → route → upkeep |
| Connection broker | Credential vault, OAuth, connectors, executing `act` |
| Store | One transactional database plus derived search indexes |
| Local bridge | Optional. An outbound-only helper on a Mac, for example for iMessage |

## Technology

Chosen for fast context retrieval, simple self-hosting, reliable concurrency and permissions, easy extensibility and minimal infrastructure.

| Part | Choice |
|---|---|
| Language | TypeScript on Node.js, for the MCP server, web app, workers and connectors |
| Database | PostgreSQL, the single source of truth |
| Database access | Plain SQL through postgres.js, with SQL migration files |
| MCP | The official TypeScript SDK over Streamable HTTP, at `/mcp` |
| Sign-in | [Better Auth](https://better-auth.com), built in: passkeys and passwords for people, and OAuth for assistants. Only the plugins Homing uses are on, and the server answers only the endpoints its pages use |
| Web app | React, built with Vite, with Tailwind and shadcn/ui. It compiles to static files the server serves; the approval card shown inside assistants compiles to one self-contained HTML file |
| Search | Postgres full-text search plus `pg_trgm` for names; pgvector only when semantic search is enabled |
| Queue | Postgres (`SKIP LOCKED`) |
| Space tree | Plain tables with recursive queries |
| Credentials | Sealed with AES-256-GCM in Postgres, under a key derived from `HOMING_SECRET` that the database never sees |
| Model access | A thin provider layer: Anthropic, OpenAI, or any OpenAI-compatible local endpoint |
| Deployment | Docker Compose: one Homing image plus Postgres. Each release publishes the image for amd64 and arm64 |

- The server code runs without a build step. Only the web app has one, and it runs when the image is built.
- One image runs every component. A setting chooses its role (everything, MCP and web, or workers), so an installation can be split later without code changes. Heavy parsing runs in worker processes.
- Each of Homing's transactions turns off PostgreSQL's JIT compilation and plans every query for its own values. Row-level security makes the planner overestimate costs, so JIT compiled queries that run in milliseconds, for up to a second, and plans cached for any values made context and search 2 to 3 times slower.
- Search looks for a query's first 32 words by letters and digits, longer ones by how they start, so "launch" finds "launches". Besides them, it looks for what PostgreSQL keeps whole in the notes it searches, as written: a number with a sign, such as the "-881" of "BETA-881", a version such as "2.4.1", a decimal, an address, a host or a path. A note with an identifier written the same way ranks above the others, and everything else is found as before. Those are quoted, so nothing in a query works as an operator.
- `context` without a space matches only a request's telling words, up to 32: PostgreSQL's English and Norwegian stopwords and numbers of one to three digits are left out, since they match nearly anything. That costs a few English words that are common in Norwegian, such as "men", "bare", "min", "sin" and "vi"; words in other languages all count. What's in an archived space is left out unless the request names it. A skill matches on its name and description, not on its files. A space is picked when the request names it, or when it alone matches and a match there has two of the request's telling words, or its only one.
- No Redis, search engine, vector database or graph database. One is added only if a benchmark shows Postgres falls short. For search, the fallback is a ranking extension inside Postgres, such as ParadeDB's `pg_search`, not a new service.
- Graphile Worker and pgvector are preferred, not committed, until they are tested.
- Homing is a server, even for one person. There is no embedded or single-binary variant in v1.

## Background work

Background work runs through a durable job queue in the same database. Workers run in the same deployment, which gives retries, concurrency control and recovery without microservices.

Jobs come in two kinds:

- **Internal jobs** (upkeep, indexing, extracting) run at least once and must be safe to repeat.
- **Publishing actions** (sending, posting, creating external records) run at most once. The attempt is recorded before acting. If the outcome is unknown, Homing never retries blindly: it checks the destination, or marks the action as uncertain and asks.

Each routine run is a job, recording who it acted for, which connection it used, what it did and which proposals it created.

## Data and security

**Every row is scoped.** Every stored row, including index entries and jobs, carries `space_id`, and `private_to` when it belongs to a private side. Jobs also record the person or space they act for.

**Row-level security is on from day one.** Homing decides what actions are authorized. PostgreSQL independently enforces who can access protected data. Normal requests and routines never bypass that protection.

- It uses the same access table and content visibility as the application, including the exceptions for guidance and proposals.
- A private item replaces a shared one only for its owner, and only through its explicit link to the item it replaces (`supersedes`), so a newer item never hides anything on its own. Shared knowledge published as a copy links to its private origin (`published_from`), which from then on shows only as the copy; changing it makes a private update of the copy, and sharing that replaces the copy for everyone.
- A person's assistant writes only on that person's private side. While an agent acts for a person, triggers refuse a new shared item, source or link in a collection, a change to a shared item, and taking a page out of a shared collection, and row-level security refuses a source added to a shared item. Homing makes an assistant's change to something shared the person's own update of it, which reaches the others once the person shares it through `publish_item`, as a direct edit. A space's routine and people editing directly write the shared side.
- The triggers that keep an item's history also keep what a person wrote from agents and routines. While an agent acts, or a space's routine, `keep_history` refuses a change to text a person wrote, and `check_replacement` refuses replacing it, counting someone named in an import as a person, and never as the person importing. The one exception is the person's own text, which they wrote themselves here, while their assistant acts for them. On their private side `keep_history` lets it change, keeps them as its author, `written_by` with no `agent`, and records the assistant in `edit_agent` on the new version, while the earlier version goes into `revisions` with whoever wrote it, so the history says who made each change. On the shared side `check_shared_side` still refuses any change, and `check_replacement` lets the assistant make only the person's own private update of it, which `keep_own_update` keeps theirs the same way, with the assistant in `edit_agent`; it reaches the others when the person shares it through `publish_item`, and a shared copy keeps the assistant too. Nothing else counts: replacing their private text, a page's title, guidance, or a routine, which acts without a person. Homing can't tell whether the person asked, and allows this only because the change is private, recorded and can be undone. Restoring an earlier version is an update with its text, by the person in the app or by their assistant, for whom `read` gives each earlier version exactly. Homing refuses an assistant's `remember` of the user's overview when the user wrote it, since the context it gives every assistant would otherwise keep it current unasked; it's changed as an item, when they ask. Upkeep isn't built yet. It will change only what routines wrote, which a space's routine writes without a person; routines that act for a person will need a mark of their own, so that what they write counts as derived and the exception never applies to them.
- A partial edit is made by the same code that updates or replaces an item, with the new text built from the old. It holds the row the change lands on, the item itself or the shared copy that stands for it, until the transaction ends, checks again that nothing has replaced it, and makes the edits to the text it has then, so a change made meanwhile is built on or refused, never undone. The result then goes through the same statement, triggers and row-level security as a whole text, held to the same 20,000 characters, and an item on an overview page to 2,000 however it's written, whole or in part, by an assistant or in the app. A passage is matched exactly, and only one that isn't there that way is matched in NFC, which then keeps the item in NFC, so an exact edit changes nothing outside its passages. `read` of a page gives an item of more than one line between Markdown fences longer than any run of backticks in it, so it shows exactly as written.
- A page's archiving is one state, a column everyone who sees the page reads. When and by whom it was archived, and its history, follow one rule, from one function that says when a person could first see a page: from the first thing on it they see, counting something shared from someone's own side from when it was shared. Row-level security shows an archive or reopening to whoever did it, and to others only from then. Homing's role can't read when or by whom from the page itself, nor who archived it before it was imported, which a column of its own keeps until it's archived or reopened here, nor when the page was made; another function gives them by the same rule, an archive from before as since then, by nobody named.
- A citation is seen with the item that cites it, checked by key for each citation, so reading a few never means reading every item there is.
- A skill's files are items on its page, each with its path, so a SKILL.md folder is stored as it was imported. For now Homing keeps only text files up to 512 KB, small enough to search, and doesn't follow links.
- Each guidance item records whether it reaches down, and a read-only policy lets shared guidance through to the spaces below, closed ones included. Private guidance needs no exception, since its owner can open its space. A trigger checks every write to a guidance or skill page: it must be a person editing directly, shared guidance needs an admin, and each page holds only its own kind of item. Only the web app and the command line mark an edit as direct, so a new path can't change guidance by accident.
- An include is a row of its own: the space whose guidance includes it, its side, and the space or skill page it points to. Removing one keeps the row, with who removed it. Row-level security shows a row where its space's guidance is seen, and only to someone who can open what it points to, and a trigger gives every write the same check as a guidance page, refusing what the writer can't open before anything else, so a refusal says nothing about it. Assembling guidance takes the includes of each space that applies at that space's level, then reads what they point to as the reader, under the ordinary policies, so an include never widens what anyone sees. It follows one step only, which is why a cycle can't loop, a rule that arrives twice is kept where it's most specific, and someone's own include of what the space also includes for everyone waits while that one is there. Each include is looked at only in the spaces that apply, before its access is checked. For a space's admins, a function returns its includes for everyone that they can't open, only their id, kind, author and date, and another stops one.
- A proposal to include something keeps what it points to in a table beside it, which row-level security shows only to someone who can open it, so an admin deciding a member's request never sees it. A proposal to stop including names the include, and what it says about it comes from the include itself.
- A proposal is on the private side of the person it's for. Assistants make them, and only that person decides one: editing directly, once, and within a week, which a trigger checks. Approving makes the change as that person, so it passes the same checks as a direct edit, at that moment, and records the decision in the same transaction. Leaving a space ends the person's access to the proposal too, so that decision is recorded before the change.
- A member's change to shared rules is a request: a proposal on the member's side that they send, which then any admin of the space sees and decides, the same way. Row-level security shows a sent request to the space's admins, and the trigger checks the decider is an admin at that moment.
- A plan, several related changes decided at once, is one proposal whose change lists its steps, each as its own proposal would hold it, and the space it creates, if any. A constraint keeps it to whole steps of the kinds a plan holds, at least two changes, and a new space only open to everyone where the plan waits, and never a request. Leaving a space is never a step. Proposing it checks each step with the code that proposes it alone. Reading it works each step out as it is now, with why it can't be made, if it can't. Approving does that again, compares what each step was shown with what's there, and runs each step's own code in order, as the person, in the transaction that decides it, so a refusal anywhere undoes the rest and names the step. Homing makes no external changes yet, so every step is inside that one transaction.
- In Claude.ai the person can also decide on a card in the conversation, an MCP App. The card's buttons reach Homing over the assistant's own connection, through tools the assistant keeps from the model. So Homing relies on the assistant for that, offers the card only to assistants checked to do it, and records which assistant's card a decision came through. Every other assistant gives the person the link.
- One restricted database role handles normal operations. Each request or routine sets its person or space for the transaction, and background workers get no elevated access.
- A separate admin role is used only for migrations and narrowly defined housekeeping, such as deletion cascades and access-table updates. The normal role can't write the access table, and changes spaces and memberships only through database functions that check the caller's rights.
- It covers sensitive data: content, sources, connections with their places, credentials and uses, and search data. Purely technical tables don't need the same policies.
- Sign-in has its own database role and schema. It can't read space data, and Homing's role can't read passwords, passkeys or sessions. An account has the same id as its person, and only accepting an invite creates both.
- The application still filters explicitly. Row-level security catches missing filters. It is not protection against a fully compromised application.

## Connections

A person connects an account from a space's Connections. Homing keeps three things apart:

- `connections`: one row for each of a person's accounts, with its connector, the account's directory or workspace (tenant) and its id there, which never change, its address and name, the permissions it granted, whether it needs attention, and when it was connected and last refreshed. Signing in with the same account again, in any space, uses the same row. A connection a space owns, for shared automation, comes with bindings.
- `places`: what a connection reaches in a space, of a kind its connector names, such as the account's own mailbox, or a company the person chose, with its name there, on one line, which the database checks has no control characters. Each is on the private side of whoever added it (`private_to`). Removing one sets `removed_at`, and revoking its connection does that to all of them, so what points to them later still finds them.
- `credentials`: a connection's refresh token and, while it lasts, its access token, each sealed.

The database keeps a connector's id and a kind as plain words, checked for their shape only, since the connectors are in Homing's code. Row-level security shows a connection only to its owner, and a place only to its owner while they can open its space, so nobody else learns of one through a list, a count, a search, an error or an id. Homing's role reads those two tables and writes neither, and can't touch `credentials` at all. Functions make every change. `connect_account`, `add_place`, `remove_place` and `revoke_connection` work only for a person editing directly, never an assistant; `connect_account` and `add_place` check the space under the shared lock on who can open which space, `add_place` only through a live connection of the person's own, and two sign-ins with the same account at once make one row of each. `credentials_of`, `keep_credentials`, `keep_refreshed` and `connection_needs_attention` work only for the connection's owner, never while an assistant acts for them; `credentials_of` hands back the sealed tokens, holding the connection's row for its short transaction. Each says the same about someone else's connection as about one that doesn't exist.

Credentials are sealed in the server before they reach the database: AES-256-GCM, under a key derived from `HOMING_SECRET` with HKDF-SHA-256 for credentials alone, with a fresh nonce each time and, as associated data, the connection's id and which token it is, so a sealed token opens nowhere else. A version byte leaves room for another key. The database, its backups and anyone with operator access to it hold only sealed bytes. After `HOMING_SECRET` changes they no longer open, so each connection needs attention until its owner signs in again. Tokens never go into a log, an error, an answer, an export or anything a model sees: no tool of an assistant's reaches them, and the functions refuse an assistant underneath.

Homing uses a connection as the person, in a short transaction of its own: the stored access token while it has two minutes left, and otherwise a refresh, keeping the new refresh token the system gives. A refresh never runs inside a transaction, since the system may take a while and nothing should wait on it holding a row or a database connection. Callers in one process that need the same connection meanwhile share one refresh, which finishes within the connector's own time limit even after they've stopped waiting, so the next use finds its tokens. `keep_refreshed` then keeps its tokens only while the stored refresh token is still the one used, and `connection_needs_attention` marks a refused one on the same condition, so a refresh that finished meanwhile, a new sign-in or revoking wins, and a revoked connection never gets credentials back. Because the database refuses to hand out tokens in a transaction where an assistant acts, nothing that runs for an assistant can fetch them. When Homing reads a place for an assistant's request (below), the server takes the tokens this way, as the person, uses them itself, and records which connection it used (spec §8); they never leave the server.

The connection needs attention when the system refuses its refresh for a reason about that account or its organization, as its connector tells, and so does one whose sealed tokens don't open. Its access token is dropped, and it isn't tried again until the person signs in again. A refusal of Homing's own configuration, such as a certificate the system doesn't know, marks no connection, and the log says which settings to check. A network failure or an outage changes nothing. Revoking deletes the credentials, so the next use finds none, without asking the system, which may have no way for an app to give back a person's consent; they withdraw it there themselves.

### Connectors

Homing standardizes how it reaches and uses a system, not how the system works. `src/connectors.ts` holds the contracts and the map of connectors, each a module in Homing's code: today Microsoft 365, set up from its settings or there but not ready without them. Nothing is installed at runtime. The server takes more connectors only from its own options, which the tests use for a stand-in.

- A `Connector` has its id, which is also how its references start and never one of Homing's own reference words, its name, what its ids are made of, what Homing may do by each permission granted, its sign-in, its kinds of place, and `refused`, which says what an error of its means: sign in again, renew a token refused before it expired, Homing's own settings, try later, or a plain refusal. Shared code decides what follows from that.
- Its sign-in is OAuth 2.0 with PKCE: the system's page for an attempt, redeeming the code that comes back, who the account is and which places connecting adds at once, refreshing, and what the person is told when connecting is refused.
- A `PlaceKind` has its words, for people and assistants, such as mailbox and email; `discover`, listing the places of the kind an account reaches, for one the person chooses; `search`, newest first, only where live search makes sense; and `read`, one item by its id.
- A connector never touches the database or stored credentials. For each use Homing hands it an `Access`: the place's resource, `token()`, which records the use before the first token and refreshes as above, and Homing's time limit as an abort signal. When the system refuses a token before it expires, one new token finds out whether the account still works.
- What it gives back is an `Item`: a thin envelope Homing handles the same way for every system (its id, title, time, author and audience, any of them unknown but the id), its fields, each with a value of a kind Homing frames (text, texts, a person, people, a time), its text where the kind has prose, what it's read with, such as a thread, and, where the kind has its own, what a source keeps of it.

The rest is shared. `connections.ts` connects, seals, refreshes and records uses. `places.ts` lists the places an account reaches for the person to choose, checking a chosen one against that list and calling `add_place` as whoever asked, so the database refuses anyone but the person in the app; finds which places a request reaches, searches and reads them under time limits, says why one couldn't be, and keeps a source. `mcp.ts` frames what comes back. A field's label is the connector's own word; its value is outside content. What's Microsoft's stays in `microsoft.ts`: the app registration and certificate, OAuth with PKCE and the client assertion, the ID-token checks, what each refusal means, Graph's calls, immutable ids and the mailbox kind. What's about email in general, the words for a mailbox, an email as an item, its audience and what a source keeps of it, is in `mail.ts`, for another email connector to use. Following changes and acting aren't built: they come as further parts of a kind, beside finding and reading.

The tests have a second connector, beside the stand-in for Microsoft, to show the shared code isn't shaped by email: Ledger, an accounting system whose companies hold invoices of fields with no prose, can't be searched live, and has places the person chooses. Its tests connect, choose a place, read by reference, frame what's read, record uses, and meet each kind of refusal.

### Microsoft 365

The connector speaks plain HTTPS to `login.microsoftonline.com/<tenant>/oauth2/v2.0`: OAuth 2.0's authorization code flow with PKCE and OpenID Connect, then two calls to Microsoft Graph.

- Starting checks that the person can open the space, then keeps the attempt for ten minutes in sign-in's own store, under a random `state`: the person, their session, the space, the connector, the PKCE verifier and a nonce, and, when they sign in again for a connection of theirs, which account that is. The browser goes to Microsoft with the S256 challenge, the state, the nonce, `prompt=select_account`, and the delegated scopes `openid profile email offline_access User.Read Mail.Read`.
- Microsoft sends the browser back to `/connections/microsoft/callback`, the address every app registration has. The state is used up by the statement that finds it, so it works once however many times the page is opened, and must be the signed-in person's, from the same session, for this connector. The code is redeemed with the verifier, and Homing proves it is the app with a client assertion: a JWT for that token endpoint, valid ten minutes, signed PS256 with the certificate's private key and naming the certificate by its SHA-256 thumbprint (`x5t#S256`). A client secret works instead, for a self-hoster without a certificate. Microsoft refuses a code used before, one that expired, and one issued for another attempt's challenge.
- The ID token comes straight from the token endpoint over TLS, which vouches for who issued it ([OpenID Connect Core 3.1.3.7](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)), so Homing checks its claims rather than its signature: this app as the audience, the attempt's nonce, an issuer of `https://login.microsoftonline.com/<tid>/v2.0`, and, on a Homing set up for one directory, that directory. The account is its `tid` and `oid`, as [Microsoft recommends](https://learn.microsoft.com/entra/identity-platform/id-token-claims-reference) for identifying a user.
- Signing in again for a connection has to bring back the same account; another one connects nothing, and the person is told. Graph's `/me` names the account, and the inbox's id, never anything in it, shows its mailbox can be read, so an account without one is refused. Only then are the connection, its mailbox as a place and its sealed tokens kept, through `connect_account` and `add_place`, in one transaction.
- The browser lands back on the space's Connections with a word for what happened, such as `connected` or `expired`, never anything Microsoft said. The log gets Microsoft's error code and AADSTS number for whoever runs Homing, never a token or a code.
- A connection needs attention when Microsoft refuses its refresh with `invalid_grant`, once consent is withdrawn or the sign-in expires, `interaction_required`, `unauthorized_client`, or `invalid_client` with AADSTS700016 or AADSTS7000112, when the organization deleted or disabled Homing's enterprise app. Any other `invalid_client` is Homing's own configuration. Graph refusing a token with `InvalidAuthenticationToken` before it expires, as after the person withdraws consent, gets one renewal.

The tests stand in for Microsoft with a small server that keeps its side of these rules, and a mailbox for each account.

### Finding and reading

An assistant's `search` and `read` reach the person's places through the server, live, never with a token of the assistant's own.

- **Which places.** The person's own places, by `private_to` and row-level security, in spaces they can open, neither removed nor revoked: those in the space searched, in a space above it (`spaces_above`) or below it (`space_subtree`), or all of them without a space. One for each thing a connection reaches, at the place in that space if there is one, else the first added. For anyone else the same small query finds nothing, so it takes the same time whatever others have connected. Context names them by kind, such as "The user's mailbox … is connected to Homing", and whether `search` reaches them or only `read`.
- **Search** asks places whose kind searches live, beside Homing's own search, outside the assistant's transaction: a transaction as the person takes the token and records the use, then the connector's search. Each place gets 2.5 seconds, the token included. Past that the answer goes out with one line for it, and what was under way finishes on its own, such as a refresh, whose new tokens are kept. For a mailbox that's Graph's `GET /me/messages?$search="…"&$top=5` with `Prefer: IdType="ImmutableId"`, newest first. Microsoft's Search API (`/search/query`) [searches messages only in work and school accounts](https://learn.microsoft.com/graph/search-concept-messages); `$search` on `/me/messages` [takes `Mail.Read` for personal accounts too](https://learn.microsoft.com/graph/api/user-list-messages).
- **References** are `<connector>:<place>:<id>`, such as `microsoft:<place>:<immutable id>`, with only what the connector's ids are made of, for Graph its URL-safe characters. `mail:<place>:<id>`, which only Microsoft mailboxes had before connectors, still reads as Microsoft's, so stored sources need no rewrite. Only that whole shape, with a connector's id in lower case and a place's id, is a reference: anything else an assistant cites, such as "Microsoft: Azure pricing page", is an ordinary citation. An [immutable id](https://learn.microsoft.com/graph/outlook-immutable-id) stays while the email moves between folders, though not to an archive mailbox. `read` looks up the place first, as the person and only among theirs, through a connection of the reference's connector, in spaces they can open, so someone else's place, or one that doesn't exist, gets the same answer before the system is asked anything. Once the place is removed or its connection revoked, the person's place for the same account, kind and resource in the same space stands for it, if they connected it there again. Otherwise the owner is told it isn't connected there any more, or that it needs attention. For an email, then `GET /me/messages/{id}`, with its `body` and `uniqueBody`, and `Prefer: outlook.body-content-type="text"`, so Microsoft turns the HTML into text and nothing in it is fetched; HTML that comes anyway is stripped to its text. The thread is `$filter=conversationId eq '…'`, at most 25 emails, attachments are read by name only, and the text shown stops at 10,000 characters.
- **Framing.** What comes from a place is either quoted as a JSON string on one line, such as a name, a subject, a field or a preview, or, for its text, fenced with more backticks than any run of them in it, the way `read` fences an item. A time is Homing's own, in UTC, and a person is their quoted name and their address. A place is named by its account's address on one line, or, for one the person chose, by the system's name for it, quoted. Neither keeps control characters, or ones that hide or turn text around: bidirectional controls, zero-width spaces, tags, variation selectors beyond the sixteen emoji use, and Hangul fillers. Both keep the joiners some scripts and emoji need, and the text its line breaks and tabs. A header says where it was read and that it's not instructions.
- **Recording.** `connection_uses` keeps each use: connection, place, space, person, what Homing did (`search`, `read`, later `follow` or an action's name), and the assistant. It's written before the token is handed out, so none goes out unrecorded. Row-level security shows a row only to its person, and takes one only for a live place of theirs. Uses are kept for 90 days: the housekeeping that tidies imports every few minutes also forgets older ones, through `forget_old_uses`, by an index on when they were used, and a failure there doesn't stop the rest of it.
- **Sources.** `remember` with a reference reads the item before its own transaction starts, then keeps the source on the person's side of the space where the place is, with `read_through` naming the connection and `audience` who could see it there, where Homing read that, such as an email's To and Cc, as `{ people, more }`. A restrictive policy takes `read_through` only there: on their own private side, in the space of a live place of theirs for a working connection. Another takes `audience` only with `read_through`, so nothing an assistant reports has one; unknown is null. What the source keeps is the kind's own, or else the item's fields, one per line, with the words given found among them. For an email, the excerpt is the From, Date and Subject lines and the words the assistant gave, 12 to 600 characters, with up to 200 characters of their paragraph on each side, cut at a word, so a "not" before them comes along, even across a wrapped line or an abbreviation. A single line break joins a paragraph, and a blank line ends it. The words are looked for, with spaces collapsed, in the email's text, never its subject. What its sender wrote is the part Exchange gives as unique to it (`uniqueBody`, as text), or, where it gives none, the text before lines starting with ">" and before a line that starts a quoted email, as Outlook and Gmail write them in English and Norwegian. Words found only in the rest are kept under a line saying the email quotes them from an earlier one, which Homing didn't read, and assistants are told so; that covers forwards and inline replies alike. Without words, the source keeps the sender's own opening, "(no text)" when they wrote nothing, and Microsoft's preview only for an email without any text. Imports never set `read_through` or `audience`, so only what Homing read here says it did, and exports leave both out, as they do connections. The app names a source as an email by the kind of place Homing read it in, the one its reference names through that connection, never by how its reference starts.

## Export and import

A space's export is a zip, read in one snapshot as the person who asks for it, so row-level security keeps everyone else's private side out underneath Homing's own filters. It goes down only through spaces the person can open, and only sources kept in those spaces come along. Items, tasks and spaces carry their own dates, as the app shows them. What happened to a page itself before the person could see anything on it stays out, by the same functions as in the app: its archive history starts when they could first see it, and a page archived before then shows as archived since then, by nobody named. Unlike in the app, that holds for their own doing too, so an export imported and exported again says the same. In knowledge, a reference such as `page:…` to anything left out keeps its words and loses the reference; rules and skills' files stay word for word, and plain Homing addresses stay as written.

```
homing.json                    what the export is, its short lists, and the files of its long ones
homing/<list>-00001.jsonl      each long list as JSON Lines, a few megabytes a file
knowledge/                     an OKF v0.2 bundle
  index.md                     okf_version, then the space's overview, tasks, sources, pages and spaces
  log.md                       what changed, by day, newest first
  <page>.md                    one concept per page
  overview.md, tasks.md
  sources/<id>.md              one concept per source
  <space>/                     each space below, the same way
guidance/
  AGENTS.md                    the space's rules
  skills/<name>/               SKILL.md folders as they were saved
  private-skills/<name>/       the person's own skills
  <space>/                     each space below, the same way
```

`homing.json` has `format: "homing-export"`, `version: 2`, the instance's address, when it was exported and by whom, the short lists `people`, `spaces`, `spaceArchives` and `includes`, and under `files` the files of each long list: `pages`, `sources`, `items`, `revisions`, `gathered`, `pageArchives`, `tasks` and `links`, an entry a line, by current ID. Version 1 held everything in `homing.json`; Homing no longer imports it, and says to export the space again. People are keys that hold only within the export, `person-1` and so on, each with a name, or null for someone the exporter no longer shares a space with; never an account's id or email. Whoever did something is an author: `by` is `person`, `agent` (with the agent's name, and the person it acted for) or `routine`. A version of an item can be a person's own text that their assistant changed for them: `person`, with the assistant as `agent`. An item has its kind, body, visibility (`shared`, or `private` to the exporter), author, when it was created and last written, what it supersedes, `onlyHere` for a rule, the sources it cites in the export, `sourcesElsewhere` for those it rests on that are kept in other spaces, and the private item it was published from when that is the exporter's own. An include has the space whose guidance it's in, its visibility, whether it waits, and what it brings in: `rules` with a space's ID or `skill` with a skill's page when that's in the export, or `elsewhere` with the space's name, and the skill's, when it isn't. Includes are read as the exporter, so row-level security and Homing's own filter both keep out anyone else's own and any of something they can't open. Removed includes aren't exported. Members, proposals, connections with their places, and credentials aren't exported, and Homing keeps no live external records yet.

Each page is a concept with its type (`Page` when it has none), `title` on one line, its id under `homing`, `generated` with the last writer as an OKF actor (`human:<name>`, `<assistant>/homing` for an agent, `process:homing` for a routine), and `sources` pointing to their concepts, cited as footnotes keyed by source id. Items keep their ids in comments, private ones say whose they are, ones resting on sources elsewhere say so, replaced ones follow under Earlier, and an archived page has `status: deprecated`. A space's AGENTS.md lists what its guidance includes under Also included, linking to the rules or the skill when they're in the bundle, and saying when they aren't. A skill's file that wouldn't stay in its folder on every system, with a backslash, a colon, `.` or `..` in its path, is left out, of `guidance/` and of the lists, since an import refuses it. A test checks the knowledge folder against OKF §11 on every change.

An export is written a space at a time, and in each space its items with their earlier versions a page at a time, at most 5,000 of them or 16 MB at once, and its sources a thousand at a time, each written to the zip as it's read. What stays in memory is a few hundred bytes a page, for links and indexes, and a space's tasks and log by day. Each long list's file closes at 8 MB or a million objects, half what an import reads of one. The zip is written with Node's own zlib to a file of its own, its list of files kept on disk beside it until the end, with ZIP64's records past 65,535 files or 4 GB, which common unzip tools read. An export stops as soon as it holds more than an import takes, 2 GB as a zip or 8 GB of long lists unpacked, and once it's whole, with `homing.json` and the zip's own records, it's held to 2 GB again. It also stops as soon as the person stops waiting for it, leaving nothing behind. Once written, Homing reads it as an import would, in a worker with less memory and time than an import has, 640 MB and 40 seconds for each file, one export at a time, and hands it out only if it would import. One that holds too much is refused with 413, saying so. One holding something an import refuses, such as a rule with a character nobody sees, which Homing keeps when it's written, is refused with 422, saying which, by its first words or its path, and to write it again, or, when it's shared and the person isn't an admin of its space, to ask one, and the reason goes to the log. One whose check took too long is refused with 503, to try again, since that says nothing about its size. Then it's sent with its length. Each person makes one export at a time, and Homing two at once, each for at most 30 minutes, and each keeps its place until its work is done and its file removed, whether or not the person still waits for it. On a laptop, the big sample's 97 spaces, 58 MB as a zip, export in about 12 seconds, and one space of 670 MB of knowledge, 176,000 items on 16,000 pages, 575 MB as a zip, in about 34. The export itself peaks under 200 MB of memory, and nothing else waits more than about 35 ms.

Import takes a zip of at most 2 GB, written to disk as it arrives, with its SHA-256, within 30 minutes, one at a time from each person and four at once. A disk that fails meanwhile refuses it, keeping nothing. Only then does it wait its turn, within those 30 minutes, saying so: Homing reads one export at a time, for a preview or an import. An export is read in a worker thread of its own, with at most 768 MB of memory and a minute for each file, telling how far it's got after each, so one made to be heavy only stops that worker while Homing keeps answering. Only `homing.json` and the long lists' files are unpacked: at most 30,000,000 files in the zip, `homing.json` at most 32 MB, each file of a long list at most 24 MB and all of them 8 GB, each with at most 2,000,000 objects and lists, counted before any is built. What a file takes up in the zip is checked before any of it is read: stored, just what it holds, and deflated, at most a little more than the most it may hold, since memory for a file's bytes isn't counted in the worker's. The worker reads a file at a time and checks each entry as it comes: format and version, every field's type, people and authors, and that it points to something that came before it in the export, in an order that holds. It also checks what the database would refuse as it's written, so what passes the check is written whole: text Homing can't keep, such as the null character, times before the year 1 however they're written, or more than 15:59 hours from UTC, and days that aren't on the calendar, an ID that comes twice, a second title on one side of a page, a collection that gathers a page twice or one without a title on its side, and a citation of a source the export doesn't hold. What can only be checked at the end, skills, includes, and rules and skills' files that hide something unless they were replaced, is checked then. Text is held to what Homing keeps: knowledge 20,000 characters, rules 4,000, the overview 2,000, titles 200, page types 40, skills' files 512 KB with one file at each place, and a skill's name in lowercase words, as its SKILL.md says. Spaces' names have no control or format characters, as Homing's own don't, rules and skills' files as they stand have none that hide or turn text around, such as direction overrides and tag characters, and spaces side by side have different names. What a rule or file said before, and one that's gone, are history nobody follows, and come in as they were, so retyping a rule is enough for its space to export and import again. Names of people and agents are shown plainly instead: on one line, without control characters or format characters that hide or turn text around, keeping the joiners, direction marks and soft hyphens languages need, as people may give them when they sign up. The preview creates nothing. It names what rules refer to in at most 80 characters, finding what came before them by reading again only the lists that hold one, picking out lines by their IDs, shows at most 1,000,000 characters of rules, and is turned into JSON in the worker, at most 5 MB of it, so whatever an export holds, what reaches the app stays small. The file stays on disk for an hour, and the import is of that file, named by its SHA-256, never sent again. Links in text are found with words that hold no brackets, so finding them takes time in step with the text. Importing gives everything a new ID, since keeping IDs where they're free would mean looking for them among others' rows, which row-level security hides and which could leak. Each comes from the old one and a key of the import's own, so references in knowledge, rules and skills' files point to the new ones without a list of them all; in rules and files, one to something the export doesn't hold stays as written. Things written in the same millisecond keep their order.

An import is then written in three steps, each a database function run with the database's own rights, as the person editing directly. `import_begin` creates the new spaces, with the person as their only admin and member, and puts them in `importing`, which keeps them out of `accessible_spaces()`: until the import is done, nobody sees them, the person importing included, in lists, counts, search or anything else. `import_load` writes a batch at a time, a file of a long list or 5,000 rows, each in a transaction of its own, and only into those spaces: every row has to land in a space the import made and point only to rows it made, or the batch is refused. Each row says which space it goes in, and nothing is joined to find it: spaces are checked against the import's, the composite keys keep items and collections in their page's space and a replacement on its page, and what rows point to is looked up by key among the import's own, so a batch takes time in step with its size, however big the import. Its checks keep their plans while it runs, and read by key, rather than being planned for each row as Homing's other queries are. `import_finish` writes the includes, makes sure nobody took the name meanwhile, and takes the spaces out of `importing`, so everything shows at once. If anything fails, `import_discard` takes out what the import wrote, and only that, a step at a time, each step a transaction of its own: at most 5,000 rows of one kind, or the items one batch wrote, found by the batch's number, which its items keep in `import_load`, the last first, since what an item replaced or was shared from came in with it or before it. Its spaces stay hidden until the last step takes them out, so however big an import, no step comes near the database's 30 seconds for a statement, and each step says the import is being worked on, so a long one isn't taken for one that stopped. One that stops without failing, as when Homing restarts, is taken out the same way by `import_discard_stale` once nothing has been written to it for 10 minutes, set in the database: Homing lists those when it starts and every 5 minutes, and takes them out one at a time, leaving one that fails for the next time; once it has started on one, it carries on with it, and the import can't write again, each checked as the import is held, so taking one out and writing to it never cross. Neither can take out anyone's import still under way, except the person's own. The app asks how far a preview and an import have got apart, so one doesn't stand in for the other, and how an import ended is said for two minutes after it's first read, as to another tab, and for at most an hour. After a big import, `import_settle` updates the tables' statistics, so what's read next is planned for what's there. Times are kept, never later than now. Nobody here is recorded as having made or written any of it: `created_by` and `written_by` stay empty, and an `imported` column on each row holds the import, the ID in the export, and who did it as the export says, by kind, person key and name, for as long as the text is theirs. A change here moves them into the history with the earlier text, and a shared copy of an imported item keeps both. The checks that keep agents from rewriting what people wrote count an imported person as a person, never as the person importing, and `sourcesElsewhere` counts among an item's hidden sources, so sharing it is never treated as resting only on what everyone sees. An earlier version is private whenever its item is or it was. `imports` records who imported what, when and from where, for whoever can open the space. Includes come in through the same check as any include, as guidance the person writes directly, with who added each and when as imported provenance, `added_by` empty, and only those of something the import made: an include in a space it didn't make, or of something it didn't bring, stops it. Those of something outside the export are left out, after the preview names them. Each space comes in archived or not, with when and by whom, and page archives come in with their imported authors, but the space archive history doesn't: each entry is visible only to whoever archived or reopened the space, so imported it would show to nobody, or be credited to the importer.

`import_begin`, `import_finish` and the last step of taking an import out take the lock that creating spaces and changing who is in them take everywhere, sign-ups included, each for a moment: how long it's held grows with how many spaces an import brings, not with what's in them, and what points to a space is found by key, however much the rest of Homing holds. On a laptop, an import holds it about 140 ms as it begins with the big sample's 97 spaces and a few as it finishes, and about 13 and 6 ms for one space of 670 MB; taking out an import that failed at the end holds it about 150 ms for the 97 spaces and 12 ms for the one, and 50 ms for 100 spaces where half a million pages and 100,000 tasks are elsewhere. The big sample imports in about 7 seconds and that space in about 100, its 575 MB zip sent and read for the preview in about 4. If that space's import fails at the end, what it wrote is taken out in about 20 seconds, in about 110 steps, none over about half a second. The worker peaks at about 140 MB of memory, and meanwhile creating a space elsewhere takes at most about 60 ms and other requests at most about 55. A small server is likely two to three times slower. A batch that takes longer than the database's 30 seconds for a statement stops the import, and nothing of it is left. A space that holds more than one export can still be moved, a space below it at a time.

## Self-hosting

Self-hosting is part of the product, not something users piece together: HTTPS, MCP authentication, OAuth callbacks, migrations, upgrades, backup and restore. A full backup includes `HOMING_SECRET`, which the key for connections' credentials comes from. A Markdown export is not an operational backup.

Migrations run as a separate step before the server starts, so the running server never holds the admin role. When the server starts and nobody looks after the instance yet, it prints the setup link for the first account. The link works once, for an hour, and only a hash of its token is kept.

Every assistant, Claude Code included, connects over OAuth to `/mcp`. It names itself with a client metadata document at its own address, so nobody registers clients, and the person signs in and allows it on Homing's own pages. Only assistants from sites the instance trusts can connect, Claude's and ChatGPT's unless it says otherwise, because each one can send people back to its own addresses. Its tokens are for `/mcp` only and are checked against Homing's signing keys locally; a token bound to the assistant's key (DPoP) also needs a fresh proof from that key. On every request Homing checks that the person hasn't disconnected the assistant, because a token alone would keep working until it expires. Disconnecting also deletes its refresh tokens and unused authorization codes. Dynamic client registration stays off until a client we test needs it.

People join through invites from the instance admin. Email is optional, over SMTP. With it, an invite can be sent by email, which verifies the address it is accepted with, and someone who can't sign in gets a one-time sign-in link at their verified address. Without it, whoever runs the server makes that link with the command line. Either way the link only signs the person in, once, so they can add a new passkey.

Until the web app and assistants can, the command-line tool also sets up spaces and imports skills. It is a stand-in, not the intended way to use Homing.

The command line and the database credentials are operator access. The command line takes any person's id without sign-in, and any connection with the credentials can mark itself as a person editing directly, so either can act as anyone, including changing guidance. An agent that can run commands where Homing runs, such as Claude Code on the same machine, has that access too. Once there is sign-in, a direct edit needs a signed-in person, and the command line keeps only what setting up an instance needs.

## Toward a hosted version

Homing is designed so it could run as a managed service, without building that in v1. Roots are organizational boundaries, not tenant isolation. A hosted service would also need identities, credentials, storage, indexes and execution kept separate per tenant.
